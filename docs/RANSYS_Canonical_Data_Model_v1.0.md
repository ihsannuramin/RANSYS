# RANSYS Canonical Data Model v1.0

**Document Type:** Detailed Engineering Design — Canonical Data Contracts  
**Product:** RANSYS Universal Transaction Switching & Processing Platform  
**Version:** 1.0  
**Status:** Engineering Baseline Draft  
**Primary Language Reference:** C# / Modern .NET  
**Depends On:** PRD v1.0, ERD v1.1, Ledger Posting Rule Matrix v1.0, Transaction State Transition Matrix v1.0, Sequence Diagram Pack v1.0

---

# 1. Purpose

Dokumen ini mendefinisikan **bahasa data internal resmi RANSYS**.

Canonical Data Model berada di antara:

```text
External Request / Protocol Message
        |
        v
Translation / Protocol Boundary
        |
        v
Canonical Data Model
        |
        v
Transaction Core
        |
        +--> Ledger
        +--> Routing
        +--> Provider Adapter Contract
        +--> Outbox Events
        +--> Backoffice Projection
```

Canonical model bertujuan agar Transaction Core tidak bergantung pada:

- format REST merchant;
- SOAP XML provider;
- ISO8583 data element;
- proprietary TCP packet;
- nama field provider tertentu;
- schema Backoffice;
- persistence shape PostgreSQL.

---

# 2. Fundamental Principle

Canonical model adalah **domain contract internal**.

Bukan:

```text
database entity
external API DTO
provider-specific DTO
raw protocol message
backoffice report model
```

Satu data concept boleh memiliki representasi berbeda:

```text
External API DTO
    -> Canonical Command
    -> Domain Aggregate
    -> Persistence Model
    -> Provider Contract
```

Boundary translation harus explicit.

# 6. Transaction ID

```text
RansysTransactionId
```

Type:

```text
Guid in C#
uuid in PostgreSQL
```

Generation:

```text
recommended UUIDv7
```

Rules:

1. Generated by RANSYS.
2. Globally unique.
3. Immutable.
4. Present in every cross-service interaction after transaction creation.
5. Not derived from STAN/RRN/client reference.
6. Must be propagated in logs/events/tracing.

---

# 7. `TransactionIdentity`

Canonical fields:

```text
RansysTransactionId
ClientReference
IdempotencyKey?
Fingerprint
OriginalTransactionId?
```

## Rules

`ClientReference`:

```text
mandatory for financial transaction
max canonical length 128
```

`IdempotencyKey`:

```text
optional/contract-dependent
not equivalent to ClientReference
```

`Fingerprint`:

```text
internal canonical duplicate detector
not client-editable
```

`OriginalTransactionId`:

used by:

```text
REFUND
REVERSAL where represented as child action
related transaction flows
```

---

# 8. Idempotency Concepts Must Stay Separate

RANSYS distinguishes:

```text
ClientReference
IdempotencyKey
TransactionFingerprint
SecurityNonce
```

They are not interchangeable.

## ClientReference

Business reference supplied by client.

## IdempotencyKey

Optional explicit API retry identity.

## Fingerprint

RANSYS hash/canonical signature of meaningful business payload.

## Nonce

Security anti-replay token.

# 12. `Money`

```text

├── CurrencyCode
├── CurrencyScale
└── CurrencyDefinitionVersion
```

C#:


```text

```

---

# 13. Money Rules

1. Amount is exact.
2. Amount cannot have fractional precision beyond the active currency definition.
3. Currency definition is captured at transaction creation.
4. Historical money object never silently changes scale/version.
5. Arithmetic requires compatible currency definition unless explicit conversion is invoked.
6. Equality includes currency definition identity, not amount only.

---

# 14. Suggested `Money` Behavior

Conceptual methods:

```text
Add(Money other)
Subtract(Money other)
IsGreaterThan(Money other)
IsZero()
ValidateScale()
```

If incompatible currency definition:

```text
throw domain validation error
```

Do not silently convert.

# 35. Timestamp Rule

Do not use:


# 37. Why Capture Configuration Versions

Example:

```text

23:00 fee config changes to 3,000

```

```text
2,500
```

because transaction terms were fixed when validated/reserved.

# 39. Metadata Governance

Metadata must not be used for fields already canonicalized.

Forbidden examples:

```text
metadata["amount"]
metadata["transactionStatus"]
metadata["providerReference"]
metadata["merchantId"]
```

Those have first-class fields.

---

# 40. Metadata Promotion Rule

If extension field becomes used by:

```text
multiple providers
multiple products
routing
reconciliation
reporting
security
```

then architecture review should consider promoting it into canonical schema.

# 170. Acceptance Criteria

Canonical Data Model v1 is accepted if:

1. Core can represent all transaction families without provider-specific fields.
2. Money never uses floating point.
3. Currency definition/version is preserved.
4. Client reference and fingerprint are separate.
5. Nonce is outside business idempotency.
6. Four state dimensions are represented separately.
7. Transaction attempts distinguish `RequestSent`.
8. ProviderResult cannot directly modify financial state.
9. Fee components support tax/provider cost/revenue split.
10. Refund references original transaction.
11. Metadata is governed and namespaced.
12. Config/routing/fee policy versions can be captured.
13. Events use explicit versioned envelopes.
14. Public API DTO is not the Domain aggregate.
15. Provider DTO is not the Domain aggregate.
16. Backoffice query model is not the write aggregate.
17. Trace/correlation identifiers are available.
18. Raw payload is referenced, not embedded as transaction truth.
19. Manual financial action includes approval/evidence reference.
20. Model maps cleanly to ERD v1.1 without becoming persistence-coupled.
